# Подключение MRAD 2.0 к своему аддону

Этот документ описывает игровые компоненты и ресурсы MRAD. Поведение проверяется в Arma Reforger; данные и сценарии здесь относятся к игре.

## Зависимость проекта

В Workbench добавьте MRAD как зависимость своего аддона. GUID проекта MRAD: **`61E9542E592789AF`**. Сам MRAD зависит от штатного Arma Reforger (`58D0FB3206B6F859`); примерам не нужны RHS или ACE.

Соответствующий элемент в `addon.gproj` вашего проекта:

```text
Dependencies {
 "58D0FB3206B6F859"
 "61E9542E592789AF"
}
```

Создавайте свои дочерние префабы через **Inherit**. Сохраняйте GUID и пути оригинальных ресурсов MRAD: дочернему ресурсу Workbench назначает собственный GUID. Не помещайте копию исходного prefab с его старым `.meta` в другой путь.

## Готовые примеры

| Ресурс | Класс прицела | Содержимое |
|---|---|---|
| `{A7DE1002B62C4801}Prefabs/Weapons/MRAD/Optics/MRAD_Optic_ARTII_2D.et` | `MRAD_2DSightsComponent` | ART II с обычным 2D ADS и отдельным состоянием поправок. |
| `{A7DE1002B62C4802}Prefabs/Weapons/MRAD/Optics/MRAD_Optic_ARTII_PIP.et` | `MRAD_PIPSightsComponent` | ART II с штатным PIP/2D переключением. |
| `{A7DE1002B62C4803}Prefabs/Weapons/MRAD/Rifles/MRAD_Rifle_M21_2D.et` | Первый прицел | M21, в attachment slot которого уже указан MRAD 2D. |
| `{A7DE1002B62C4804}Prefabs/Weapons/MRAD/Rifles/MRAD_Rifle_M21_PIP.et` | Второй прицел | M21 с MRAD PIP. |

У оружия сохраняются штатные игровые компоненты, модель и магазин. Примеры добавляют отдельные ресурсы и не переопределяют vanilla M21 или ART II. Названия берутся из StringTable MRAD.

Для этих четырёх ресурсов фактический spawn в server runtime 1.9.0.37 подтверждён: `MRAD_OpticsProbe` прошёл 49 проверок без ошибок, включая точный 2D-класс без остаточного vanilla PIP, attachment в обоих M21, replication ID и независимость состояния. Отдельный настоящий server/live-client/JIP-client запуск `network-20261116T151544271791Z` подтвердил передачу ticks и notebook snapshot, включая изменение в активном сеансе и новое подключение. Точные границы и evidence приведены в [RESEARCH_OPTICS.md](RESEARCH_OPTICS.md); ADS-допуск production RPC и попадания проверяются отдельно.

## Компоненты прицела

На **одной entity** оптического прицела нужны:

1. Ровно один `MRAD_2DSightsComponent` либо `MRAD_PIPSightsComponent`.
2. Ровно один `MRAD_ZeroingStateComponent`.
3. Рабочая унаследованная replication hierarchy предмета, включающая state-компонент.

Для собственного обычного прицела используйте наследника `MRAD_2DSightsComponent`; для PIP — наследника `MRAD_PIPSightsComponent`. Их родительские классы — соответственно `SCR_2DSightsComponent` и `SCR_2DPIPSightsComponent`. Если нужны новые editor attributes, также создайте соответствующий наследник `*ComponentClass`.

При адаптации существующего prefab замените его sights-компонент, сохранив его component ID и совместимые свойства сетки, точек прицеливания, FOV и native zeroing. Не добавляйте второй конкурирующий sights-компонент рядом с первым. Замена типа должна быть проверена фактической загрузкой prefab; компиляция класса не доказывает корректность наследования ресурса. Для первого рабочего варианта проще наследовать готовый MRAD-пример.

У `MRAD_ZeroingStateComponent` есть два editor attributes:

| Поле | Значение по умолчанию | Назначение |
|---|---:|---|
| `m_fElevationLimitMrad` | 50 | Максимальная по модулю дополнительная вертикальная поправка этого prefab. |
| `m_fWindageLimitMrad` | 50 | Максимальная по модулю дополнительная горизонтальная поправка этого prefab. |

Пределы симметричны. Действующий предел — минимум значения prefab, настройки сервера и настройки игрока; абсолютный предел протокола равен 50 MRAD. Пользовательская настройка может сузить разрешённый диапазон. На dedicated server настройки читаются из профиля сервера, при отсутствии файла используются значения по умолчанию.

Изменяемое состояние хранится в **экземпляре** `MRAD_ZeroingStateComponent`: четыре `RplProp` для двух поправок и двух подтверждённых пределов. Единица хранения — целая десятая MRAD. `ComponentClass` не хранит текущие поправки, поэтому два одинаковых prefab имеют независимое состояние. Перенос одного предмета между игроками сохраняет его значения в текущей сессии. Сохранение между перезапусками сервера не реализовано.

### Authority и камера

Клиент отправляет через принадлежащий ему `SCR_PlayerController` дельту одной оси или сброс. Сервер проверяет управляемого персонажа, ADS, состояние персонажа и точное совпадение state с его текущим прицелом. Он ограничивает шаг и итоговое значение, затем реплицирует состояние. Клиентская камера читает подтверждённые значения; локального предсказания нет.

Отдельное согласование пределов при входе в ADS и после изменения настроек получает server ACK. Только этот запрос с нулевой дельтой можно повторить при раннем ADS/streaming переходе: до восьми попыток через 0.5 с. Реальные шаги ввода повторно не отправляются. При исчерпании попыток появляется диагностическое предупреждение; следующий вход в ADS или изменение настройки запускает согласование заново.

`GetCameraLocalTransform` дополняет результат `super` поворотом локальных осей камеры и сохраняет её позицию. `GetMisalignmentAngles` учитывает тот же поворот в системе отсчёта сетки. Штатные callbacks zoom, illumination, PIP и far observer остаются через `super`.

Поправка MRAD **добавляется к текущему native zeroing**. Значение HUD `0.0 / 0.0` означает отсутствие добавочного поворота; штатная дальность прицела при этом остаётся выбранной. Сброс MRAD также не меняет native range. Таблица блокнота и добавочная поправка прицела не являются автоматически связанными абсолютными величинами: блокнот не вводит значения в оптику.

Не вызывайте `ForceSightsZeroValue` для игровой реализации: установленная документация помечает его как Workbench-only. Не добавляйте второй поворот в projectile/muzzle callbacks — MRAD использует линию прицеливания камеры, а штатный игровой выстрел остаётся штатным.

## Ввод и настройки игрока

Откройте **Настройки → MRAD**. На этой вкладке находятся параметры блокнота, fine/coarse шаги, пределы оптики, переключатель HUD и строки переназначения клавиш. Те же действия доступны в категории **MRAD** стандартного раздела управления. Захват клавиш, комбинаций и сохранение выполняет штатный `InputBinding`.

| Действие | Имя action | По умолчанию |
|---|---|---|
| Вертикальная поправка вверх, fine | `MRAD_ElevationUpFine` | ↑ |
| Вертикальная поправка вниз, fine | `MRAD_ElevationDownFine` | ↓ |
| Горизонтальная поправка влево, fine | `MRAD_WindageLeftFine` | ← |
| Горизонтальная поправка вправо, fine | `MRAD_WindageRightFine` | → |
| Вертикальная поправка вверх, coarse | `MRAD_ElevationUpCoarse` | Shift + ↑ |
| Вертикальная поправка вниз, coarse | `MRAD_ElevationDownCoarse` | Shift + ↓ |
| Горизонтальная поправка влево, coarse | `MRAD_WindageLeftCoarse` | Shift + ← |
| Горизонтальная поправка вправо, coarse | `MRAD_WindageRightCoarse` | Shift + → |
| Сброс добавочных поправок | `MRAD_ResetZeroing` | Не назначено |

Fine и coarse по умолчанию равны 0.1 и 1.0 MRAD. Обе настройки кратны 0.1; fine допускает 0.1–5, coarse — 0.1–10. Сброс назначьте на свободную клавишу в меню: штатная перезарядка не переопределена.

Контекст `MRAD_OpticsContext` активируется только у локального игрока с поддерживаемым активным прицелом в ADS. При открытом меню подписки снимаются; при выходе из ADS удаляется и HUD. Глобальная регистрация слушателей в вашем моде не нужна.

Параметры MRAD сохраняются в `$profile:MRAD/settings.json`; клавиши сохраняются штатной системой профиля отдельно. После **Применить** параметры действуют без перезапуска. Уменьшение предела оптики согласуется с сервером и ограничивает уже сохранённую поправку.

## Наследование блокнота

Существующие ресурсы сохраняют свои GUID и пути:

| Ресурс | Использование |
|---|---|
| `{D30D4FA5A82D6F0D}Prefabs/Items/Equipment/RangeCard/RangeCard_Notepad_Base.et` | Статический текстовый блокнот, основа собственных variants. |
| `Prefabs/Items/Equipment/RangeCard/RangeCard_Notepad_AUTO.et` | Динамическая таблица оружия из weapon slot index 0. |

`Drg_NotepadRtComponent` сохраняет имя класса и поля `m_sPathLayout`, `m_sText`. Для статического дочернего prefab задайте свой текст и при необходимости layout. Для AUTO сохранён класс `Drg_AutoNotepadRtComponent`; строка `m_sText = "script"` в старом prefab остаётся совместимой, но динамическая таблица строится компонентом.

В базовом prefab lifecycle теперь обслуживает `MRAD_NotepadGadgetComponent`, наследник штатного `SCR_DataDisplayGadgetComponent`. Взяли предмет в руки — открывается RT; убрали, передали или удалили — RT отсоединяется до удаления виджетов. В Workbench edit mode RT не создаётся. На сервере расчёт и page state работают без workspace.

Если сторонний prefab **явно заменял gadget-компонент**, ему нужно перейти на `MRAD_NotepadGadgetComponent` либо совместимый наследник. Одного добавления render-компонента к произвольному предмету недостаточно: lifecycle должен вызывать `OpenFor(character)` и `Close()`. Глобального override всех `SCR_GadgetComponent` больше нет.

Для старого текстового layout нужны `drg_Main_RTTexture` (`RTTextureWidget`) и `drg_Text` (`RichTextWidget`). AUTO использует три колонки нового layout; при отсутствии контейнера `mrad_Dynamic` остаётся простой текстовый fallback. У нового layout сохраните именованные виджеты `mrad_Bullet`, `mrad_Suppressed`, `mrad_RangeHeader`, `mrad_DropHeader`, `mrad_WindHeader`, `mrad_Ranges`, `mrad_Drops`, `mrad_Winds`, `mrad_Status`, `mrad_Page`.

Страницы переключаются item actions `MRAD_ChangeNotepadPageAction` с `m_iStep = 1` и `-1`. Actions видны только владельцу блокнота в руках и только при нескольких страницах. Сервер подтверждает страницу и передаёт готовые строки таблицы наблюдателям; им не требуется локально читать магазин другого игрока. Запросы также идут через владеемый `SCR_PlayerController`.

Сохранены публичные entry points AUTO `RecalculateWidget`, `GetMuzzleFromWeapon`, `CalculateRadians`. Поля внутренних виджетов и старый алгоритм не являются совместимым API: стороннему скрипту следует вызывать публичные методы, а не сохранять ссылки на старые UI-поля.

### Игровые данные ветра для своего снаряда

Калькулятор сначала использует штатную wind table, затем доступный native diagnostic predictor. Для обычного **`ShellMoveComponent`** без доступных native данных предусмотрен `MRAD_GameShellWindModel`: он читает `Mass` и `AirDrag` из фактического `IEntitySource` и использует `Physics.VGravity`. В коде этого fallback нет списка патронов, внешних таблиц или коэффициентов, подобранных под M118.

Порядок численного обновления и шаг 1/30 с установлены сравнением с диагностическим predictor установленной 1.9.0.37. Проверка двух независимых игровых ресурсов M118/M855, трёх коэффициентов скорости 0.8/1/1.01, ветра ±4/±30 и строк 100–1500 прошла **360 из 360** сравнений; максимальное расхождение составило 0.00239563 MRAD при допуске 0.2. Это подтверждение указанной игровой матрицы, а не всех будущих изменений движка или сторонних movement-компонентов.

Другой класс движения, отсутствующие/некорректные поля, нестабильные параметры или исчерпанный расчётный бюджет дают `NoWind` и прочерк в соответствующих строках. Для нестандартного снаряда предоставьте native wind config или отдельно проверьте совместимость его модели. Fallback сохраняет отдельную пометку расчётной модели в интерфейсе. История исследования и точные evidence runs находятся в [RESEARCH_RUNTIME.md](RESEARCH_RUNTIME.md).

## Совместимость с другими модами оптики

ACE Scopes также меняет camera angles родительской оптики. Независимые поправки могут складываться; MRAD не отключает функции ACE и не обращается к его внутренним полям. Совместная работа не объявляется проверенной до отдельного игрового теста. Для исходного теста MRAD используйте набор модов без ACE Scopes, затем отдельно проверьте требуемую комбинацию.

Изменения через `modded` ограничены добавлением RPC-методов `SCR_PlayerController` для блокнота и оптики, а также добавлением MRAD-вкладки `SCR_SettingsSuperMenu`. MRAD не заменяет логику всех vanilla sights. При конфликте другого мода с этими точками расширения проверьте итоговую цепочку наследования и вызовы `super`.

## Проверка своего prefab

Компиляцию, проверку ресурсов и проверку игрового результата проводите отдельно:

1. Скомпилируйте классы текущим Workbench. Проверьте точный тип sights-компонента загруженного prefab, отсутствие второго vanilla sights и наличие одного state на той же entity. Проверьте, что `Replication.FindItemId(state)` валиден в server runtime.
2. В игре проверьте вход/выход ADS, меню, новые бинды, zoom, illumination, PIP/2D переключение, reset и оба предела. Создайте два одинаковых прицела: изменение одного не должно менять другой.
3. Для MP используйте server и два клиента. Проверьте ввод владельца, отображение реплицированных значений, перенос прицела и позднее подключение. Повторите с более узким пределом нового владельца.
4. Для AC-11 используйте настоящую тестовую сцену игры: один клиент стреляет штатным вводом, второй наблюдает неподвижную тестовую поверхность, сервер записывает фактическое место попадания. Сравнивайте исходный вариант и вариант с поправкой после повторного наведения той же ADS-метки. Сохраняйте run/shot ID, ticks, native range, матрицы камеры/оружия и серверное попадание. Одно лишь изменение камеры при неподвижном оружии не доказывает изменения траектории.

В `tools/qa/MRAD_QA` находятся отдельные development helpers: `MRAD_OpticsMathChecks` проверяет реальную `Math3D`, `MRAD_OpticsProbe` загружает/создаёт четыре примера и проверяет классы, replication IDs, независимость состояния и server clamps. Эти helpers не входят в runtime addon и не являются доказательством прохождения MP/попаданий. Фактический статус выполненных проверок фиксируется отдельно в отчёте верификации.

Сигнатуры, источники установленной версии и ограничения camera-подхода описаны в [RESEARCH_OPTICS.md](RESEARCH_OPTICS.md).
